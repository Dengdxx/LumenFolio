# 帧格式与兼容性

两种格式都表示整幅 1200×1600，保留原来的六色码：`0` 黑、`1` 白、`2` 黄、`3` 红、`5` 蓝、`6` 绿。每字节存两个像素，偶数列占高半字节；像素按行排列，每行 600 字节。压缩只作用于文件和传输，不改变画质、显示驱动或现有双缓冲大小。

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 4 | 魔数 `EPD1` 或 `EPD2` |
| 4 | 8 | 小端 `uint16 x,y,w,h`，固定为 `0,0,1200,1600` |
| 12 | 4 | 仅 EPD2：小端 `uint32`，表示后续 zlib 载荷的字节数 |

EPD1 从偏移 12 起直接存 960000 字节像素，总长 960012。EPD2 从偏移 16 起存标准 zlib 流，包含 zlib 头和 Adler32；解压结果恰好是 960000 字节像素，不含 EPD1 帧头。编码器只有在 EPD2 的整个文件比 EPD1 更小时才选压缩，否则原样回退 EPD1。[Go 编解码器](../app/pc/panel/frame.go)和 [Python 产帧工具](../tools/make_frame.py)使用同一布局。微信小程序[上传](../app/miniprogram/README.md#取景与传图)生成 EPD1。文件扩展名为 `.bin`。

固件的 [`epd_frame` 组件](../components/epd_frame)供 Flash 资产和 TF 卡共用：验证尺寸、输入边界、完整流结束、无尾随压缩数据、Adler32 和固定输出长度后才送屏。显示任务解码时复用已有两块 PSRAM 缓冲，只在堆上额外分配 miniz 状态，不再申请整帧，也不把解压状态放在任务栈上。Flash 的开机槽与上传槽仍各为 1 MiB；文件缩小不自动增加槽数，上传仍擦除整个槽。资产帧的完整读取与擦除、写入互斥，避免下一次上传覆盖正在读取的上一帧。

新固件可直接读取已有 EPD1；旧固件不能读取 EPD2，必须先升级固件，再上传新帧或烧录压缩开机图。应用 OTA 不改写已有资产，设备上的旧图不会被自动转换。

## 易错点（务必遵守）

- 导出的文件在旧固件上打不开 → 旧固件只识别 EPD1 → 先升级固件，再传输或烧录 EPD2。
- HTTP 上传长度错误 → 服务端要的是实际编码帧长度，EPD2 比 EPD1 短 → 发送 `.bin` 原始字节和实际 `Content-Length`，不要再用 HTTP gzip。见[上传接口](控制接口.md#上传并查询送屏进度)。
