# 屏幕控制接口

面板在断电、重启后仍保留画面，冷启动不主动刷屏。机身按键、HTTP 和串口控制台都可以触发刷新。HTTP 的默认端口为 `8080`，也可通过[蓝牙回环](bluetooth.md#传输边界)访问相同的路由。只在可信网络使用 HTTP。

一次整帧刷新约 35 秒。刷新期间到达的命令会在这一轮结束后合并成一次动作，不会排队连刷。

## 易错点（务必遵守）

- 请求找不到包含中文、空格、加号或百分号的文件 → 直接拼接 URL 会改变参数的含义 → 按 UTF-8 对 `id` 和 `after` 做百分号编码。SD 列表和翻页只读根目录，文件名最多 95 个 UTF-8 字节。
- 文件能列出却无法预览 → 列表只检查帧头和长度，不能排除损坏的压缩数据 → 预览端应按[帧格式](frames.md)完整解码，成功后再显示。
- `POST /frame/display` 返回 HTTP 202，画面却没换 → 202 只表示刷新请求已经排队 → 等待面板完成刷新；若日志显示读图失败，检查原始文件。读取失败时面板保留原画面。

## 画面来源

没有点选来源时，原地重刷先读 SD 卡上的当前帧，其次是 artifacts 的开机画面，最后回退到白屏。上一张、下一张只在 SD 卡根目录的 `.bin` 帧文件间按文件名顺序循环；没有可用帧时不换图。

局域网传图可写入 Flash 上传槽或保存到 TF 卡。Flash 上传槽 `inbox` 存放最近一次上传，开机画面 `boot` 独立保存。设备保存后安排刷屏。

```powershell
.\app\pc\LumenFolio.exe --host <设备IP> frame 照片.png
```

图形界面的操作见[第一次传图](quickstart.md)。用旧接口直接上传已编码的 EPD1／EPD2 帧到 Flash：

```powershell
curl.exe --fail-with-body -H "Content-Type: application/octet-stream" --data-binary "@画面.bin" "http://<设备IP>:8080/frame"
```

`POST /frame` 只接受固定 `Content-Length` 的 `application/octet-stream`，长度须等于整个编码帧的实际字节数且不超过 960012。支持整幅 EPD1 原始帧和 EPD2 zlib 无损压缩帧，布局见[帧格式与兼容性](frames.md)；直接上传 `.bin`，不使用 HTTP gzip。

帧头可以跨多次接收，验证尺寸和总长度后才擦除上传槽。先写载荷与其余帧头，最后单独写魔数，未收完的帧不会被识别。202 只表示已写入。看响应正文判断是否排上刷新：队列不可用时会返回「已写入，屏幕还没排上刷新」。即使排上也不代表已经通过解码校验；显示任务完整解码后才送屏，错误帧记录日志而不上屏。

## 上传并查询送屏进度

| 请求 | 结果 |
| --- | --- |
| `POST /frame/transfer?source=artifacts` | 写入 Flash 上传槽，202 返回 `{"id":123}` |
| `POST /frame/transfer?source=sd&id=photo.bin` | 保存到 SD 根目录，202 返回 `{"id":123}` |
| `GET /frame/transfer?id=123` | 返回 `{"stage":"queued","message":"已保存，等待发送到面板"}`；记录不存在时返回 404 |

两个上传地址使用与旧接口相同的内容类型、定长和帧格式约束。SD 文件名须是根目录的 `.bin` 文件名，最长 95 个 UTF-8 字节，作为 `id` 参数百分号编码。设备校验完整的 EPD1／EPD2 数据和六色色码，把原始编码帧写入根目录的保留临时文件 `LumenFolio-upload.tmp`，关闭成功后才改为目标名。已有同名文件或目录时返回 409，保留原件。未挂载返回 503，卡满返回 507，帧校验失败返回 422。

202 表示画面已保存，可按返回的正整数 ID 查询本次送屏结果。设备保留本次开机的活动记录和最近结束的记录，共 16 条。刷新命令仍按原规则合并，送屏被后续命令替代时，该 ID 会进入 `failed`。Flash 的上传或删除、SD 的删除若与该来源仍在等待送屏的上传冲突，返回 409。

| 阶段 | 含义 |
| --- | --- |
| `queued` | 已保存，等待显示任务或正在读取画面 |
| `spi` | 显示任务正在向面板发送画面和刷新命令 |
| `done` | 像素与刷新命令已经发出，屏幕继续完成约 35 秒的刷新 |
| `failed` | 画面已保存，送屏失败，原因见 `message` |

```powershell
curl.exe --fail-with-body -H "Content-Type: application/octet-stream" --data-binary "@photo.bin" "http://<设备IP>:8080/frame/transfer?source=sd&id=photo.bin"
curl.exe --fail-with-body "http://<设备IP>:8080/frame/transfer?id=123"
```

## 浏览板端画面

浏览、预览和查询容量只读取数据。显示请求读取选中的 Flash 槽或 SD 文件并排队刷新。同步请求处理期间暂停自动深睡，缩略图请求入队时刷新空闲计时。

| 请求 | 结果 |
| --- | --- |
| `GET /frames?source=artifacts` | 列出 Flash artifacts 分区的有效画面，`boot` 为开机画面，`inbox` 为最近一次上传的画面 |
| `GET /frames?source=sd` | 列出 SD 卡根目录的有效 `.bin` 帧文件，ID 为实际文件名 |
| `GET /frames?source=sd&limit=<条数>&after=<游标>` | 按文件名分页列出 SD 卡帧，`limit` 取 1 至 32，第一页省略 `after` |
| `GET /frames/storage` | 查询 Flash artifacts 和 SD 的已用字节数及总字节数 |
| `GET /frame?source=<artifacts 或 sd>&id=<画面 ID>` | 返回头部声明长度的 EPD1／EPD2 编码帧，类型为 `application/octet-stream`。画面不存在返回 404 |
| `GET /frame/thumb?source=<artifacts 或 sd>&id=<画面 ID>` | 返回 120×160 行优先小端 RGB565，`application/octet-stream`，固定 38,400 字节。画面不存在返回 404，队列满返回 429，任务或工作区不可用返回 503 |
| `POST /frame/display?source=<artifacts 或 sd>&id=<画面 ID>` | 空请求体。202 表示刷新已排队，400 表示参数或请求体不合要求，404 表示画面不存在，503 表示显示任务暂不可用或队列满 |
| `DELETE /frame?source=<artifacts 或 sd>&id=<画面 ID>` | 空请求体。204 表示已删除，400 表示参数非法，403 表示开机画面受保护，404 表示画面不存在，409 表示该来源有上传正等待送屏，422 表示 SD 文件帧头无效，503 表示 SD 卡未挂载，500 表示存储错误 |

列表响应形如 `{"available":true,"frames":[{"id":"boot","name":"开机画面"}]}`。SD 卡已挂载但没有画面时返回 `available:true` 和空数组，未挂载时返回 `available:false` 和空数组。

分页列表按不区分大小写的文件名字典序返回。响应的 `next` 是下一页游标，末页为空字符串。传下一页时对 `next` 做 URL 百分号编码后放入 `after`。每项的 `revision` 用卡标识、文件大小和修改时间区分同名文件的缓存版本。旧请求省略 `limit` 时仍返回原来的最多 32 项。

容量响应形如 `{"artifacts":{"used_bytes":960012,"total_bytes":11927552},"sd":null}`。Flash 已用量是两个有效帧的编码长度之和，总量是整个 artifacts 分区的容量。SD 采用文件系统报告的容量和空闲空间，已用量包含卡上的所有文件。未挂载或无法读取的来源返回 `null`。

缩略图由单独的低优先级任务串行解码，每块 10×10 像素的近似墨水色做面积平均。最多处理一项并等待一项，队列满时客户端可短暂退避重试。响应仍通过原 HTTP 请求返回。相框使用独立 PSRAM 工作区解码帧，并在请求结束后释放。App 点开完整预览时读取 `/frame`。

积压的点选命令在同一轮处理时取最后一个，优先于同时积压的翻页和重刷。更晚到达的传图或出厂画面命令会覆盖点选。成功显示 SD 图片后，翻页从该文件的序号继续。本次开机内原地重刷时读取上次选中的来源，一次整帧刷新约 35 秒。

删除会移除 SD 根目录中的有效帧文件，或擦除 Flash 的上传槽 `inbox`。面板在删除后继续保留当前画面。原地重刷时若上次点选的原件已缺失，显示任务会清掉该点选记录并回到默认来源。

```powershell
curl.exe --fail-with-body -X DELETE "http://<设备IP>:8080/frame?source=sd&id=photo.bin"
```

## 按键

| 键 | 引脚 | 动作 |
| --- | --- | --- |
| KEY1 | GPIO3 | 上一张 |
| KEY2 | GPIO8 | 下一张 |
| KEY3 | GPIO18 | 短按原地重刷；长按约两秒打开[蓝牙连接窗口](bluetooth.md) |

KEY1 和 KEY2 由下降沿触发，消抖窗口为 60 ms。KEY3 检测按下和释放；松开时确认短按，长按触发广播后松手不再重刷。按住不连发。

## 控制台

串口和 HTTP 用的是同一套命令：语义只有一份实现，回执文本也完全相同。日常操作走 HTTP 就行，串口留着看日志。

| 命令 | 动作 |
| --- | --- |
| `n` / `next` | 下一张 |
| `p` / `prev` | 上一张 |
| `r` / `refresh` | 重刷当前这张 |
| `f` / `factory` | 显示出厂画面（artifacts 分区里那张） |
| `s` / `sleep` | 立即进入深度睡眠 |
| `awake` / `hold` | 本次开机不再自动睡眠，直到复位或 `sleep` |
| `status` | 运行状态与睡眠诊断 |
| `help` / `?` | 命令表 |

**串口**：USB-SERIAL-JTAG，和日志同一个口，115200。按行输入，**回车执行**，支持退格，输入会回显。

**HTTP**：`GET /console?cmd=<命令>`，回执就是纯文本。

```bash
curl 'http://<设备IP>:8080/console?cmd=next'
curl 'http://<设备IP>:8080/console?cmd=status'
```

`status` 的输出形如：

```
wake=cold display=idle last=ok frames=1 idx=0 plugged=0 usb=1 idle=4200ms sleep=off-powered
battery=3828mV 64% 未接充电
env=28.0C 21.0%RH
sd=mounted
heap=172435/138412 psram=6460180
```

- `wake`：本次启动的唤醒源，`cold` 冷启动 / `timer` 定时 / `key1`–`key3` 按键。
- `display`：显示任务状态，`starting` / `idle` / `busy` / `dead`。`dead` 表示它初始化失败已经退出，屏不会再刷新——看 `last` 和日志定位。
- `last`：最近一次显示任务结果。常见值有 `ok`（显示成功）、`load-failed`（加载或送屏失败）、`no-image`（无图可翻页）、`epd-init-failed`（面板初始化失败）、`no-fb`（帧缓冲不可用）。完整取值见[显示任务](../main/main.cpp)。
- `plugged`：TP4056 报告正在充电或已充满。`usb`：USB 主机已枚举设备。
- `sleep`：`off-powered` 插着电或连着电脑不睡 / `hold` 被 `awake` 钉住 / `waiting` 还在等空闲窗口 / `due` 空闲已满 5 分钟，仍可能受显示、OTA 或蓝牙活动阻止。
- `heap`：内部 RAM 的当前空闲 / 历史最低空闲，和 PSRAM 空闲。分配失败类问题先看这个。

返回里的 `queued` 表示命令已入队，不代表动作已经做完——一次整帧刷新要几十秒。

设备地址的获取方式见 [Wi-Fi 连接](quickstart.md#改用-wi-fi)。深睡中的相框不响应串口和无线请求，先用机身按键唤醒。完整规则见[低功耗与深睡](低功耗.md)。
